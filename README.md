# piecemeal

A Rust library for generating Protocol Buffers messages in an incremental fashion.

## about

Everything about `piecemeal` is centered around building Protocol Buffers messages incrementally, without having to
create the entire message in memory before serializing it. While it's very easy to generate message structs that allow
for borrowed representations of fields (such as using `&'a str` instead of `String`), this can quickly fall apart as
soon as there is any nesting. To say it out loud, this crate **does not** generate code to allow for deserializing
Protocol Buffers messages.

For example, we can trivially write out a struct for `Person` that allows for borrowing the relevant values, but
`Persons` would require us to store values using the generated types internally, which means utilizing the
generated Protocol Buffers types in domain code, which isn't great:

```proto
# A non-nested and nested message:
message Person {
  string name = 1;
  int32 age = 2;
}

message Persons {
  repeated Person persons = 1;
}
```

```rust
// We can write this one to allow for borrowing:
struct Person<'a> {
  name: &'a str,
  age: i32,
}

// We have to choose one of the following forms for `Persons`,
// though, which requires either allocating or using the generated
// types internally, both of which can be very unergonomic:
struct PersonsWithAlloc<'a> {
  persons: Vec<Person<'a>>,
}

struct PersonsWithoutAlloc<'a> {
  persons: &'a [Person<'a>],
}
```

Additionally, working with the generated types means that there is no way to trivially/lazily populate repeated fields
without allocating. In some specialized use cases, it can be advantageous to serialize repeated fields directly into the
output stream to minimize memory usage and avoid allocations. This is possible due to the specification of Protocol
Buffers allowing fields to be serialized in any order, but it's not generally supported by the type of code generated by
Protocol Buffers libraries.

## usage

`piecemeal` works similarly to most other Protocol Buffers code generation crates, taking in `.proto` files and
generating code. However, what `piecemeal` generates are a series of _builders_, which should look familiar to anyone
who works with builder-style APIs. Let's look at an example below:

```proto
message MetricPayload {
    message MetricPoint {
        double value = 1;
        int64 unix_timestamp = 2;
    }

    message MetricSeries {
        string name = 1;
        repeated string tags = 2;
        repeated MetricPoint points = 3;
    }

    repeated MetricSeries series = 1;
}
```

This Protocol Buffers definition is used for writing out metrics data, and we can immediately see that there's an
encapsulating "payload" message that holds multiple series, and each series has a name, tags, and points. Let's see what
the generated code looks like and how we might use it:

```rust
let mut payload_builder = MetricPayloadBuilder::new(&mut scratch_writer);
payload_builder.add_series(|series_builder| {
	series_builder.name("metric.name")?
	.add_points(|pb| {
		pb.unix_timestamp(1234567890)?.value(42.0)?;
		Ok(())
	})?;

	Ok(())
});
```

We've omitted some of the necessary boilerplate and error handling for brevity, but let's examine what's going on in
this code snippet:

- we create our `MetricsPayload` builder, and we generally work from the outside in (`MetricsPayload` -> `MetricSeries`
  -> `MetricPoint`)
- builders have methods for fields, which are either the field name itself for singular fields, or `add_<field name>`
  for repeated fields
- singular field methods take the value in a borrowed form when possible (i.e. `&str` instead of `String`) or the actual
  type for primitive scalar types (e.g., `f64`)
- repeated field methods take a closure that provided a builder for the relevant field type (e.g., the dedicated builder
  type for messages, or a generic builder for scalar types)
- map fields utilize a generic map builder that allows for arbitrary key/value pairs utilizing the relevant types

At a high level, we can see that the design pushes users towards typed builders that are actually mapped to the relevant
fields in the Protocol Buffers message, rather than having to manually write out field tags or anything else that would
normally be required to generate a Protocol Buffers message incrementally.

## supported features

- [x] non-nested messages
- [x] nested messages
- [x] repeated fields
- [x] map fields with scalar keys/values
- [ ] map fields with scalar keys and complex (message) values
- [ ] enums
- [ ] oneof fields
- [ ] packed types
